# tree-sitter-hvp

A [tree-sitter](https://tree-sitter.github.io/tree-sitter/) grammar for the HVP
(Hierarchical Verification Plan) language used by Synopsys Verification Planner.

**Status: Phase 6 done.** `grammar.js` parses HVP's block structure — the 7 block-pair
keywords (`plan`/`endplan`, `feature`/`endfeature`, `metric`/`endmetric`,
`measure`/`endmeasure`, `override`/`endoverride`, `filter`/`endfilter`,
`until`/`enduntil`, where `until` is a 3-way branch with `elseuntil`/`else`), statements
inside each block, comments, strings (with `${...}` interpolation), and numbers — plus a
`queries/highlights.scm` mapping the parse tree to standard tree-sitter highlight capture
names. It exists so [`zed-hvp`](../zed-hvp) can register `hvp` as a real Zed language;
Zed's extension API requires a tree-sitter grammar for any language registration, with no
LSP-only path (see `../MIGRATION.md`'s Decisions log, 2026-08-12).

See `../MIGRATION.md` for the overall plan, phase checklist, and current status.

## Package layout

```
grammar.js            ← the grammar itself (tree-sitter DSL)
tree-sitter.json       ← grammar metadata Zed/tree-sitter-cli read (scope, file-types, highlights path)
queries/highlights.scm ← highlight query: grammar node types → standard capture names
src/                    ← generated by `tree-sitter generate` (parser.c, node-types.json,
                          grammar.json) — committed, per tree-sitter grammar-repo
                          convention: consumers (Zed included) build from this checked-in
                          C source rather than regenerating it themselves
test/corpus/*.txt       ← `tree-sitter test` corpus: input + expected S-expression tree,
                          one file per language feature area
```

## Setup

```
npm install
npm run generate   # tree-sitter generate — (re)builds src/ from grammar.js
npm test           # tree-sitter generate && tree-sitter test — runs test/corpus/*.txt
```

Parsing a real file directly (useful for eyeballing the tree or hunting `ERROR` nodes):

```
npx tree-sitter parse path/to/file.hvp
```

## What this grammar does and doesn't do

This grammar turns valid and near-valid HVP into a sensible parse tree for syntax
highlighting. It deliberately does **not** re-implement every semantic rule
[`hvp-language-server`](../hvp-language-server)'s `analyzeBlocks()` already checks —
mismatched/orphan/unclosed blocks are the language *server*'s job (via LSP diagnostics),
not this grammar's. Where real HVP is ambiguous or a construct is malformed,
tree-sitter's built-in error recovery produces `ERROR`/`MISSING` nodes rather than
failing outright — verified against `../hvp-language-server/test/fixtures/*.hvp`
(including its deliberately-invalid fixtures, which correctly produce `ERROR`/`MISSING`
nodes) and against the full 2554-line `../mipi_dphy.hvp` real-world plan, which parses
with zero `ERROR` nodes.

## Source of truth

`grammar.js`'s keyword/block-pair structure mirrors
`../hvp-language-server/src/core/keywords.ts` (`BLOCK_OPEN_KEYWORD`/`BLOCK_CLOSE_KEYWORD`/
`NON_PAIRED_KEYWORDS`/etc.) — that file is the canonical keyword table already shared by
the LSP server and the two regex-based generated grammars
(`../hvp-language-server/tools/gen-grammars.ts`). This grammar is a different, harder
kind of artifact than those: it describes real syntax *structure* (a parse tree), not
just token classification, so it isn't generated from `keywords.ts` the way the
TextMate/sublime-syntax grammars are — it's hand-written, informed by that table and by
the language spec (`../hvp-documentation/Using the HVP Language.md`).
